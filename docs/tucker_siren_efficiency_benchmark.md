# SIREN vs Tucker-SIREN: computational efficiency and 3D FWI performance

This study compares two implicit neural representations of the material model
inside DeepGPR's CUDA FDTD / discrete-adjoint FWI: a standard SIREN evaluated
at every grid cell and a Tucker-SIREN, in which 1D SIRENs generate Tucker
factor matrices that DeepGPR's `tucker_reconstruct` turns into the full model.
Dense voxels and direct Tucker factors (no network) are the references.

All networks are external experiment code (`examples/tucker/siren_comparison/`,
not part of the DeepGPR package). They reuse `DeepGPR.tucker.tucker_reconstruct`,
`TuckerTensor` and `hosvd`, the native CUDA FDTD and the discrete adjoint
unchanged. Wavefield Tucker sketching is OFF in every run: only the model
parameterization differs.

Three quantities are kept apart throughout:

1. the number of coordinates at which a network is evaluated,
2. the number of trainable parameters,
3. the GPU memory and run time of a complete FWI iteration.

They are not equivalent. Reducing (1) from `N_x N_y N_z` to `N_x + N_y + N_z`
does not imply a matching reduction of (2) or (3), and none of the speed-ups
below is derived from point counts; all are measured.

## 1. Definitions

**Property mapping (all methods).** Taken from the existing SIREN-IFWI code
(`~/sirenifwi3d`, `MultiScaleSiren3D.get_params`):

```
eps_r   = eps_min + (eps_max - eps_min) * sigmoid(t_eps)            eps in (1, 10)
log10 s = log_min + (log_max - log_min) * sigmoid(t_sigma)          sigma = 10**log10 s
```

with `log_min = log10(sigma_min + 1e-9)`, `sigma_max = 1.25 max(sigma_true)`.
The methods differ only in how the unconstrained fields `t_eps`, `t_sigma`
are produced.

**Standard SIREN.** `f_theta : R^3 -> R^2`, `(x, y, z) -> (t_eps, t_sigma)`,
evaluated at all `N = N_x N_y N_z` cell centres in `[-1, 1]^3`. Layers
`sin(omega_0 (W h + b))` with Sitzmann initialisation (first layer
`U(-1/n, 1/n)`, others `U(-sqrt(6/n)/omega_0, sqrt(6/n)/omega_0)`, `omega_0 = 30`),
`L` sine layers of width `W`, a linear output layer. Default `4 x 128` (50 306
parameters). Grids that do not fit are evaluated in chunks under the
reentrant `torch.utils.checkpoint` (the existing notebooks' scheme): each chunk
is recomputed and back-propagated on its own, gradients are exact (Test:
`tests/test_tucker_siren_experiment.py`).

**Tucker-SIREN.** Per property `p in {eps, sigma}` (independent, no shared
factors):

```
U_x^p = f_{theta_x^p}(x) in R^{N_x x r},  U_y^p = f_{theta_y^p}(y),  U_z^p = f_{theta_z^p}(z)
t_p   = G_p x_1 U_x^p x_2 U_y^p x_3 U_z^p,    G_p in R^{r x r x r}  (trainable)
```

i.e. six 1D SIRENs (`1 -> r`, default `2 x 32`) and two cores in 3D. The
networks generate the factor matrices directly; no full model is ever
decomposed. `t_p` is computed by `DeepGPR.tucker.tucker_reconstruct` with the
full autograd graph.

**Direct Tucker.** `t_p` = `DeepGPR.tucker.TuckerTensor` (core and factors
optimised directly, `"rms"` factor normalisation), initialised by HOSVD.

**Dense.** `t_p` stored per voxel.

## 2. Analytic operation counts (`flops.py`)

Per generation of both properties on an `N_x x N_y x N_z` grid (multiply-add = 2
FLOPs; sines are counted separately because they run on the special-function
units):

```
C_SIREN        = 2 N (3 W + (L-1) W^2 + 2 W)              sines: N L W
C_TuckerSIREN  = sum_{p, n} 2 N_n (W + (L-1) W^2 + W r)   sines: 2 (N_x+N_y+N_z) L W
C_recon        = 2 x [2 r^3 N_a + 2 r^2 N_a N_b + 2 r N_a N_b N_c]   (DeepGPR's order, two properties)
```

The last term of `C_recon` (`4 r N` for both properties) scales with the full
grid: the reconstruction is not free. For `120 x 120 x 100`:

| | network FLOPs (fwd) | reconstruction FLOPs (fwd) | sine evaluations |
|---|---|---|---|
| SIREN 4 x 128 | 1.45e11 | 0 | 7.4e8 |
| Tucker-SIREN 2 x 32, r = 16 | 2.2e6 | 1.06e8 | 4.4e4 |
| Tucker-SIREN 4 x 128, r = 16 | 7.1e7 | 1.06e8 | 3.5e5 |

The profiler's GEMM FLOP counts agree with the analytic counts (forward +
backward = 3x forward, e.g. 9.8e9 vs 3 x 3.3e9 at 32^3). For Tucker-SIREN 98 %
of the floating-point work is the reconstruction, not the networks.

## 3. Experiment A - model generation without FDTD

One iteration = generate `(eps_r, sigma)`, contract with a fixed random
cotangent (stand-in for the FDTD gradient, identical for all methods),
backward, Adam step. RTX 4090 (local, exclusive; desktop compositor only),
PyTorch 1.11, strict float32 (TF32 off), 5 warm-up + 20 timed iterations,
CUDA events (GPU timeline), synchronized wall clock, kernel time and launch
count from `torch.profiler`, peak allocated / reserved memory, each
configuration in its own process. Full tables: `results/full/report_tables.md`
(generated by `report.py` from `results/full/generation.json`).

Forward + backward + Adam step (CUDA events, mean of 20):

| grid | SIREN 4x128 | SIREN 4x128 chunked | T-SIREN 2x32 r16 | T-SIREN 4x128 r16 | speed-up (full / chunked) | peak memory SIREN / chunked / T-SIREN 2x32 |
|---|---|---|---|---|---|---|
| 50^3 | 7.3 ms | - | 2.36 ms | 3.56 ms | 3.1x | 0.61 GiB / - / 6 MiB |
| 100^3 | 50.1 ms | 71.5 ms | 2.60 ms | 3.73 ms | 19x / 28x | 4.80 / 1.30 GiB / 46 MiB |
| 120x120x100 | 72.6 ms | 102.6 ms | 2.62 ms | 3.87 ms | 28x / 39x | 6.91 / 1.31 GiB / 63 MiB |
| 160^3 | 203 ms | 304 ms | 2.54 ms | 3.86 ms | 80x / 120x | 19.6 / 1.43 GiB / 180 MiB |
| 200^3 | OOM | 594 ms | 2.67 ms | 3.86 ms | - / 222x | OOM / 1.61 GiB / 342 MiB |

What the measurements show:

* **SIREN** cost scales with the cell count (kernel time = CUDA-event time:
  compute-bound GEMMs); its autograd graph holds the activations of every
  cell (5.66 GiB at 120 x 120 x 100). Chunked checkpointed evaluation trades
  ~40-50 % more time (recomputation) for a near-constant 1.3-1.6 GiB.
* **Tucker-SIREN** time is almost independent of the grid up to 200^3 and of
  the network width: the iteration launches ~540 small kernels (~880 for
  4 x 128) whose execution takes only 0.9-2.1 ms; the rest is launch latency
  (CUDA-event 2.4-2.7 ms vs kernel 0.9-2.1 ms). Its memory is the output
  model, the reconstruction intermediates and the mapping (all
  `O(N_x N_y N_z)` but a few tensors, not `L W` activations per cell).
* The generation-stage speed-up therefore grows with the grid (3x at 50^3,
  28x at the FWI size, 222x at 200^3 against chunked SIREN) and stays two
  to four orders of magnitude below the coordinate ratio
  (`N / (N_x + N_y + N_z)` = 833 ... 13 333).
* A Tucker-SIREN with the same per-network size as the SIREN (4 x 128, 6.3x
  more parameters: 319 328) is still faster by 2x (50^3) to 19x
  (120 x 120 x 100) and 150x (200^3, chunked SIREN): the cost is set by the
  number of evaluated coordinates, not by the parameter count.
* Same parameter budget (group C, +-1 %): SIREN 4 x 76 (18 014) vs T-SIREN
  2 x 32 r16 (18 080): 42.9 vs 2.62 ms, 4.22 GiB vs 63 MiB at
  120 x 120 x 100; SIREN 4 x 128 (50 306) vs T-SIREN 2 x 75 r16 (50 588):
  72.6 vs 2.48 ms.
* The Adam step of Tucker-SIREN (1.0 ms, many small parameter tensors,
  PyTorch 1.11 without fused/foreach Adam) costs as much as its forward pass.

Profiling of the reconstruction (`profile_reconstruction.py`,
`results/full/reconstruction_profile.json`): forward + backward of one
property takes 0.23-0.34 ms for every order of the three mode products at
120 x 120 x 100 and 200^3 (r = 8-24), DeepGPR's built-in order is within
5 % of the best order, and a single `torch.einsum` is 10-30 % slower. The
reconstruction is not a bottleneck, so no optimisation was applied.

Time to reach a relative eps L2 error of 5 % / 3 % / 2 % / 1 %: SIREN 4 x 128
23 / 46 / 76 s / not within 3000 steps (1.02 % at the end); Tucker-SIREN r 16
4.6 s / not reached; r 24 3.2 s / not reached; 2 x 64 r 32 1.5 / 3.6 s / not
reached.

* **Rank limit, not network capacity.** At r = 16, widening the factor networks
  changes the error from 0.349 (2 x 16) to 0.252 (2 x 32), 0.247 (2 x 64),
  0.240 (2 x 128) and 0.239 (3 x 64), approaching the direct-Tucker value at the
  same rank (0.235). Only the 2 x 16 networks are capacity-limited. The
  representation floor is the Tucker rank: 6.0 / 5.1 / 4.1 / 3.2 / 2.2 % at
  r = 8 / 12 / 16 / 24 / 32, each within 1.01-1.16 x of the direct-Tucker error.
* **SIREN is more accurate, Tucker-SIREN reaches moderate accuracy sooner.**
  The SIREN reaches 1 % relative error (SSIM 0.98) where Tucker-SIREN stops at
  2-4 %; Tucker-SIREN reaches 5 % 5x sooner (4.6 vs 23 s) with 1/45 of the
  memory.
* **Conductivity.** The Tucker-SIREN log10 sigma error is 0.042-0.043 for every
  rank, 1.6-4.4x the direct-Tucker value at the same rank: the 1D factor networks
  fit the sharp air/ground step of log10 sigma (from -9 to about -2.4) poorly.
* **Not every configuration trains.** Tucker-SIREN 4 x 128 r 16 diverged with
  the common learning rate 1e-3 (eps RMSE 1.49); SIREN 4 x 256 at 1e-4
  converged more slowly than 4 x 128 within 3000 steps. Learning-rate checks
  (SIREN 3e-5 / 3e-4, Tucker-SIREN 3e-4 / 3e-3) did not change the ranking.

## 5. Experiment C - FWI with DeepGPR

### 5.1 Set-up

* **2D:** the 2D FWI notebook at its own size (`examples/2DFWImodel.npy`,
  200 x 100, dx 5 cm, dt 50 ps, 200 MHz Ricker, nt 2000, 50 shots in one batch,
  receivers on the last row, 10-cell CPML, mode 2).
* **3D:** the 120 x 120 x 100 model of the Tucker FWI benchmark (dx 2 cm, dt 30 ps,
  500 MHz, nt 600, 4 shots, 100 surface receivers, mode 3).
* Observed data from the true model with the same solver (inverse crime,
  identical for all methods); loss `0.5 sum ||d - d_obs||^2 / sum ||d_obs||^2`;
  uncompressed default history (no wavefield sketch, no checkpointing) for every
  method; eps and sigma inverted jointly.
* **Initial model** (all methods): smoothed true eps, constant sigma (the mean).
  Each parameterization is pre-fitted to it (dense: exact; direct Tucker: HOSVD;
  SIREN: full-grid Adam, lr 1e-3 cosine, 3000 steps; Tucker-SIREN: 1D networks
  fitted to the balanced HOSVD factors, then joint fine-tuning). Pre-fit times
  are reported separately and are cached per (method, seed); the relative eps
  difference to the initial model after pre-fitting is <= 0.7 % for every method.
* **Learning rates** by a 15-iteration search over four values per method (from
  the same pre-fitted state, criterion: mean of the last three losses, divergent
  runs excluded); its cost is reported. Adam, 150 (2D) / 100 (3D) iterations,
  three seeds for the network methods (seeds change the network initialisation;
  dense and direct Tucker are deterministic).
* **Timing per iteration:** model generation, FDTD forward (all shots),
  discrete adjoint (all shots), network backward, optimizer step, separated by
  back-propagating the FDTD loss to detached copies of `(eps, sigma)` first and
  then through the parameterization (identical gradient to a single backward).
* 2D ran on server GPU 5 (another user's idle process held 3 GiB), 3D on server
  GPU 7 (exclusive); all methods of one case on the same GPU.

What the 3D runs show:

* **Cost.** FDTD forward + adjoint are 2.27-2.28 s of every iteration
  (97 % for SIREN, 99.8 % for Tucker-SIREN). The SIREN network stage
  (generation + network backward + Adam) costs 61.8 ms, the Tucker-SIREN r16
  stage 3.55 ms: `S_network = 17.4`, but `S_FWI = 2.346 / 2.294 = 1.023`. The
  network stage is too small a share of the iteration for its speed-up to
  matter.
* **Memory.** The SIREN's autograd graph (5.5 GiB at this grid) lives while the
  four FDTD shots run, so the FWI peak rises from 16.06 GiB (dense, direct
  Tucker, all Tucker-SIRENs) to 21.57 GiB: Tucker-SIREN lowers the peak by
  5.5 GiB (26 %). Chunked SIREN evaluation (Experiment A) would remove most
  of that at ~40 % more network time (not run in FWI).
* **Pre-fit.** Matching the common initial model costs SIREN 185 s (the time
  of ~80 FWI iterations) and Tucker-SIREN 11 s; including it, 100 iterations
  take 420 s (SIREN) vs 240 s (Tucker-SIREN r16).
* **Accuracy.** Tucker-SIREN r12-r24 reach the lowest data losses (7-9e-5, two
  to five times lower than SIREN, lower than dense) and the lowest eps errors
  (0.463-0.467; zone 0.504-0.516 vs dense 0.537, SIREN 0.552). The structural
  similarity tells a different story: dense reaches the highest eps SSIM
  (0.462) and the only visible shallow layering (Fig. 7), the Tucker-SIRENs
  0.426-0.428, SIREN 0.437. All inversions stay close to the initial model
  (eps RMSE changes by <= 0.02 out of 0.48): four shots, an 18 ns record and
  100 iterations constrain the model only weakly, so the accuracy ranking has
  limited resolution. Rank 8 is too low (eps worse than the start).
* **Conductivity.** All Tucker parameterizations damage sigma: log10 sigma RMSE
  0.26-0.40 (Tucker-SIREN r12-r24, direct Tucker) and 1.01 (r8) vs 0.11 for
  dense and SIREN (which barely change sigma), with axis-aligned stripes along
  the surface (Fig. 7), as in 2D.

### 5.4 Round 2 (protocol v2, after review of round 1)

Review of the round-1 figures: the initial model was too close to the truth
(four passes of a 9-cell box filter, effective Gaussian width ~5 cells, which
kept the ellipse and the dipping layer), and sigma came out poorly for SIREN and
Tucker-SIREN. Causes found: (1) sigma = 0 S/m in the air made the log10 mapping
span 1e-9 ... sigma_max (6.6 decades), so the subsurface sat on the flat top of
the sigmoid (derivative ~0.05) and (2) the air/ground step became a jump of
~12 logit units, which a separable low-rank model cannot represent (the stripe
below the surface in round 1); (3) eps and sigma were updated jointly from the
first iteration although sigma is far less sensitive.

Protocol v2 (`bench_fwi.py --protocol v2`, results in `results/full_v2/`),
identical for every method:

* start = Gaussian-smoothed true model with width 10 cells (3D) / 20 cells (2D),
  for eps and for sigma, as in `examples/2.2DFWI.ipynb`, `examples/3.3DFWI.ipynb`
  and the SIREN-IFWI notebooks (initial eps RMSE 0.575 in 3D, 0.748 in 2D,
  vs 0.48 / 0.44 in round 1);
* the air layer is fixed at its true values and is not parameterized (3D);
* sigma mapping range from the subsurface (0.5 x minimum ... 1.5 x maximum,
  ~1.7 decades in 3D);
* eps only for the first third of the iterations, then eps and sigma
  (`examples/2.2DFWI.ipynb`); 150 (3D) / 200 (2D) iterations;
* new learning-rate search, three seeds; data, solver and loss unchanged.
  Seven 3D runs failed with OOM because another user's process took GPU 3
  during the run; they were rerun on free GPUs (logs in `results/full_v2/logs`).

From the poorer start, the SIREN is the only parameterization that improves both
eps and sigma; it recovers the dipping layer and the round anomaly (Fig. 7,
`results/full_v2/figures`). The dense inversion (learning rate chosen by the
data loss over 15 iterations) fits the data with ring artefacts around the
sources and a worse model. Tucker-SIREN and direct Tucker produce blocky,
axis-aligned patterns in eps and sigma: the circle and the dipping layer are not
separable, and a low-rank Tucker model is a poor prior for them. Note that the
learning rate is chosen by the data loss after 15 iterations; with this poor
start that criterion prefers the fastest data fit (dense lr 0.1), not the best
model. The SIREN eps RMSE is lowest after ~20 s (0.586) and rises slightly
afterwards (0.606 at 200 iterations).

Overall accuracy verdict across both rounds: the Tucker parameterizations
are not more accurate than SIREN or dense in a way that holds across cases;
in 2D from a poor start they are clearly worse than the SIREN, and their
separable structure produces stripe artefacts in sigma (and in eps when the
learning rate is large).

#### Why the 2D Tucker stripes are vertical

The 2D case is a crosshole geometry: sources on the left edge of Fig. 7
(y = 0), receivers on the right edge (y = ny - 1), waves travel along y.
A separable model produces cross artefacts in both directions, but the data
remove only one of them (`stripe_check.py`, `results/full_v2/stripe_check.json`):

* adding 0.3 cos(2 pi y / L) to the true eps (stripes varying along the
  propagation direction, vertical in Fig. 7) raises the loss to 1e-3 ... 3e-3,
  the same stripes along x to 1.3e-2 ... 1.6e-1 (6-86 x more, L = 4 ... 20 cells):
  transmission integrates along the path, so variations along it cancel;
* removing the vertical-stripe part from the Tucker-SIREN r16 result
  (rms 0.20) raises its loss from 0.0087 to 0.0116, removing the
  horizontal-stripe part (rms 0.10) raises it to 0.0182;
* the first dense gradient is nearly isotropic (vertical/horizontal 1.17),
  the true update is mostly horizontal (0.53), the Tucker results are
  vertical (1.3-2.5).

The vertical stripes therefore sit in the near null space of the data;
nothing in the v2 objective removes them.

Changes from v2 (`bench_fwi.py --protocol v3`, `results/full_v3/`,

  improves (0.683 -> 0.49-0.62). SIREN (0.486) and dense (0.498) are best,
  Tucker-SIREN r24 0.523, the other Tucker models 0.56-0.62; dense resolves the

* Below 40 cells, i.e. beyond what the 18 ns record reaches, every method
  moves away from the start (0.506 -> 0.63-0.96), so the whole-model RMSE
  rises. Dense: Adam turns the tiny deep gradients into full-size steps
  (vertical streaks); Tucker models: the global factors carry shallow updates
  into depth (r16: a column of blobs below the centre). In this 3D case the
  zone RMSE, not the whole-model RMSE, measures accuracy.
* Sigma does not change during the eps-only phase, except for the SIREN, whose
  shared network moves sigma with eps (0.061 -> 0.044 after 5 iterations).
  Once sigma is updated (iteration 50) it becomes worse for every
  parameterized method: Tucker-SIREN 0.21-0.32 with horizontal bands pushed to
  the mapping bounds, direct Tucker 0.23, SIREN 0.12; dense leaves it unchanged.
  Cause: sigma uses the learning rate chosen by the 15-iteration search, which
  lies entirely in the eps-only phase, so the sigma step size is never tested;
  with a weak sigma gradient and Adam's per-parameter normalisation the shared
  low-rank sigma factors take large coherent steps. Round 2 has the same
  flaw (with 4 shots the effect was small).
* Cost results are unchanged: SIREN +1.5 % time and +5 GiB peak, all
  Tucker models as dense.

Accuracy verdict after three rounds: the SIREN is the most accurate
parameterization (2D eps and sigma, 3D zone eps); the Tucker models, with
or without SIREN factors, are not more accurate than dense or SIREN, and
produce stripe artefacts in the directions the data constrain least. Open
protocol issues: a sigma learning rate (or step limit) that is selected
in the joint phase, a learning-rate criterion that does not reward the
fastest data fit (dense lr 0.1 hurts in 2D and in the deep 3D part), and
3D evaluation restricted to the illuminated zone.

## 6. Answers

| question | answer (measured) |
|---|---|
| Does Tucker-SIREN reduce the SIREN forward computation? | Yes. 120 x 120 x 100: network forward FLOPs 1.45e11 -> 2.2e6 (+1.06e8 reconstruction, which then dominates); network forward 28.8 -> 0.41 ms, generation incl. reconstruction and mapping 28.9 -> 0.64 ms. The point ratio (1.44e6 / 340 = 4235) overstates the measured gain by two orders of magnitude, because the small Tucker-SIREN kernels are launch-bound. |
| Does it reduce the autograd backward computation? | Yes in the network stage: backward 43.7 -> 0.97 ms (analytic 2.9e11 -> 2.2e8 FLOPs); the backward of the reconstruction and mapping takes 0.51 / 0.65 / 1.30 ms (50^3 / 120 x 120 x 100 / 200^3, decomposed measurement) - comparable to the network backward (0.52 / 0.62 / 0.36 ms) and growing with the grid. Not in the FWI: the discrete adjoint (1.45 s) is unchanged. |
| Does it reduce GPU memory? | Model generation: 7.08 GiB -> 63 MiB peak (120 x 120 x 100); 19.6 GiB -> 180 MiB at 160^3; 200^3 runs where the unchunked SIREN does not fit. Complete 3D FWI: 21.57 -> 16.06 GiB (-26 %), the remainder being the FDTD history. 2D FWI: no measurable difference (10.38 vs 10.30 GiB). |
| Does it reduce the total FWI time? | Barely: 2.346 -> 2.294 s per 3D iteration (`S_FWI = 1.02`, `S_network = 17`); 2D unchanged (0.320 vs 0.319 s; there the Tucker-SIREN network stage is even slower than the SIREN's, 3.7 vs 2.2 ms, launch-bound at 20 000 points). Including the pre-fit, a 100-iteration 3D run takes 240 s vs 420 s. |
| Fewer trainable parameters at equal accuracy? | For the data misfit in 3D FWI: yes (18 080 parameters reach a 5x lower loss than the 50 306-parameter SIREN). For representing the true model: no - SIREN 4 x 128 reaches 1.0 % error, Tucker-SIREN stops at the rank floor (4.1 % at r 16, 2.2 % at r 32 with 103 744 parameters); Tucker-SIREN reaches 5 % with 3x fewer parameters and 5x sooner. |
| Does the low-rank constraint reduce resolution? | Yes (both rounds; Section 5.4: in 2D from the poorer start Tucker-SIREN eps RMSE 0.75-0.86 vs SIREN 0.61). The representation error is set by the rank (direct Tucker at the same rank is within 1.16x); sharp structures (the air/ground step in log10 sigma, thin layers) are approximated by separable sums, which produces axis-aligned stripes in sigma in 2D and 3D FWI and lower eps SSIM than dense in 3D. |

Summary: in this set-up Tucker-SIREN makes the *network* cheap (3x at 50^3,
28x at the FWI grid and up to 220x at 200^3 in the generation stage; about
100x less memory) and
removes the SIREN's 5.5 GiB activation overhead from the 3D FWI peak, but the
FWI time is set by the FDTD solver and is unchanged. Accuracy is limited by
the Tucker rank and conductivity suffers from separable-structure artefacts.

## 7. Problems and directions

* **Launch-bound small networks.** Tucker-SIREN generation needs ~540 kernel
  launches for < 1 ms of kernel work; batching the six 1D networks into one
  grouped network (block-diagonal weights or `torch.bmm` over networks) and a
  fused Adam step would cut the 2.5 ms per iteration, but cannot change the FWI
  time (2.3 s of FDTD).
* **Rank vs resolution.** Ranks >= 24 (or multi-block / hierarchical Tucker,
  or a Tucker base plus a dense or SIREN residual) are needed for sharp
  layers; the 1D factor networks are not the limit beyond 2 x 32.
* **Conductivity.** A separable model is a poor prior for sigma here; a lower
  rank or stronger smoothing for sigma, or a non-Tucker sigma, should be
  tested.
* **Optimiser.** Adam on factor networks oscillates early (Fig. 6); per-group
  learning rates for cores and networks, or L-BFGS, were not tested in this
  study.
* **Chunked SIREN in FWI.** Would remove most of the SIREN's memory penalty
  at ~40 % more network time; not run.
* **Limits of this study.** One synthetic model per dimension, inverse crime,
  four 3D shots (too few to separate the methods by 3D accuracy), 100-150
  iterations, no regularisation (the notebooks' TV term and gradient
  normalisation were not used), learning rates chosen by data loss, three seeds, PyTorch 1.11 (local) and 2.0.1
  (server) on RTX 4090s; the 2D runs shared their GPU with an idle process of
  another user. Five seeds were not run.
